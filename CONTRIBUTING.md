# Contributing

## Setup and checks

Use Node.js 22.5+ and Python 3.11+. Git, npm, and Make must be on `PATH`.
Run all commands from the repository root:

```sh
npm ci
make hooks-install
make verify
```

`make verify` runs:

- Changeset parser, Git hook, and release-flow tests in disposable repositories (`make changeset-test`).
- Pending changeset, manifest/lockfile, and upstream-base validation (`make changeset-status`).
- TypeScript typecheck and the Node test suite (`npm run check`), including thin-client policy and release-rule tests.

After changes to session restore (`src/session/`), anchors, or `/agy sessions`, also run `npm run test:e2e-resume` (needs `pi` and `tmux`, runs only against its mock `agy`). Never run live tests against a real `agy` from scripts or agents.

## Changesets

This repository uses a small Python changeset flow, not `@changesets/cli`.
Every non-merge, non-release commit adds one new Markdown changeset in `.changeset/`.
Write notes for changelog readers, not as copies of commit messages.

For documentation, tests, formatting, or internal tooling without a release note, add an explicit empty changeset.
Editing a note from an earlier commit does not count as a new changeset.
Do not bypass the pre-commit hook.

Interactive entry:

```sh
make changeset
```

Non-interactive entry:

```sh
python3 -B scripts/changeset.py add --type fixed --bump patch "What changed for the user."
python3 -B scripts/changeset.py add --empty
```

Stage the generated file with the change it describes. Example note:

```markdown
---
type: fixed
bump: patch
---

What changed for the user.
```

| Field | Values |
| --- | --- |
| `type` | `added`, `changed`, `fixed`, `removed` |
| `bump` | `patch`, `minor`, `major` |

The highest pending bump wins. Bumps do not add together.
Only stable `X.Y.Z` versions are generated by `make version`.

An empty changeset contains two `---` lines. It generates no note or version bump.
The next release with real notes consumes pending empty changesets too.

Do not rewrite published changelog history.
A changeset is neither release authorization nor evidence of acceptance.

### Hook behavior

Install the hook once per clone with `make hooks-install`.
The installer preserves existing hooks and `core.hooksPath`; integrate `check-staged` into an existing hook manager instead.

The hook checks staged content, not unstaged edits:

- Merge commits use notes from the merged branches. Staged notes still need valid syntax.
- Amend checks use the commit's parent, so the original note counts.
- Deleting pending changesets outside a release commit is rejected.
- Release commits must exactly match the generated `package.json`, `package-lock.json`, `CHANGELOG.md`, and consumed notes.

## Prepare a release

Prepare a version only after an explicit release request, on clean `main` with verified, committed changesets.
Use `make version`, not `npm version` or a manual edit:

```sh
make changeset-status
make version
make verify
git diff --check
git add package.json package-lock.json CHANGELOG.md
git add -u .changeset
git commit -m "chore: release <version>"
make release-check
```

`make version` plans all outputs before writing. It:

1. Selects the highest pending SemVer bump.
2. Reads the current upstream base from `docs/upstream/CHANGELOG.md`.
3. Updates the version in `package.json` and `package-lock.json` without resolving dependencies.
4. Prepends a dated `CHANGELOG.md` section (including `Upstream base: pi-antigravity-bridge X.Y.Z.`) and removes all consumed changesets.

It does not commit, tag, push, or publish.
`make release-check` verifies clean `main`, synchronized manifest/lockfile without `publishConfig`, no pending changesets, an exact changeset-generated release at `HEAD`, and the full check suite.

Feature branches keep their changesets until merge. For pushing, tagging, and npm Trusted Publishing through GitHub Actions, follow [RELEASE.md](RELEASE.md).
